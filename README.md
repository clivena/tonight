# 今晚

> 今晚排好，明天照着做。

一个每日便签：**在你想规划的时候把要做的事写下来，第二天打开就是一份可以随手勾掉的清单。**

v0.3 起多了一个**独立的「记账」面**；v0.4 给这个面加了**月历**；v0.5 把记账的输入从「打字」改成「点标签」。
v0.6 是三件事一起做：**主题可以换**（五套配色）、**自定义背景图**、**标签变成自己的**，以及新增的第四个面 —— **日记**。
v0.6.1 把最后一个不统一的地方收掉：四个 Tab 背景色完全一致。
v0.7 把深色还回来，但这次是**你自己按的** —— 顶栏一个月亮，四屏同时变暗。
v0.8 让背景图可以调清楚：一根滑杆控遮罩浓度，同时把图片的导入分辨率从 1600 提到 2560 —— 后一件才是「图糊」的真正原因。

- 平台：Android（`minSdk 26` / `targetSdk 35`）
- 技术：Kotlin + Jetpack Compose + Room
- 数据：纯本地存储，**无账号、无联网、无数据收集**
- 状态：v0.8.0，已编译验证（见「验证记录」）

---

## 为什么做这个

大多数待办 App 的逻辑是「帮你记住」。但真正消耗人的不是「记不住」，而是「**不知道该先做哪个**」。

于是它们给你列表、优先级、进度条 —— 让你在动手之前先做一轮排序决策。

这里想做的事正相反：**把「决定做什么、按什么顺序」提前到你精力还够的时候做完，第二天早上不用再想。**

## 从 v0.1 到 v0.2：三条硬规则的复盘

v0.1 为了把判断力消耗压到最低，定了三条硬规则：早上**只显示一件事**、一天**最多 5 件**、规划完**就结束**。

自己用了一周之后，三条全部出了问题 —— 不是理念错，是**手段太硬**：

| v0.1 的规则 | 真实使用中发生的事 |
|---|---|
| 早上只给一件事 | 排第一的那件暂时做不了（要等人回消息、环境没准备好），整天就卡死在那里，没有任何跳过的入口 |
| 一天最多 5 件 | 上限校验写成了「全部条数」而不是「未完成条数」—— 删掉一条想换一条，就再也加不回来了 |
| 规划完就结束 | 点完「就这样」停在一句「晚安」上，当天想再补一件事也进不去，只能杀掉 App |
| 计划写完不能改 | 错字、顺序不对、不想做了 —— 全都没办法 |

**这些不是理念错了，是把手段当成了目的。**

「不给选择」是手段，目的是「不消耗判断力」。而当手段本身开始消耗判断力 —— 还得记着别踩上限、还得祈祷第一件能做、还得担心写错一个字就废了 —— 它就从帮手变成了负担。

于是 v0.2 把三处硬规则拆掉，换成：

| 原来 | 现在 | 有意保留的是什么 |
|---|---|---|
| 只给一件 | 给完整清单，**任意顺序勾选** | 顺序仍是你自己排的，界面不做二次排序 |
| 最多 5 件 | **没有上限** | —— |
| 规划完就结束 | 顶部「今天 / 规划」**两个 Tab 随时互达** | 不用退出重进，规划是随时能回去改的 |
| 计划不能改 | 可改文字、可调顺序、可删除、可取消勾选 | —— |

一句话概括：**v0.1 帮你把决定做完，v0.2 允许你改主意。**

## v0.3：为什么记账是「另一个 Tab」

这个 App 从立项起就写了一条硬规则：**不做统计、不做分类标签**。因为这些东西都在增加判断力消耗。

而记账天生就是统计。所以 v0.3 没有把记账揉进任务流里，而是**把它做成第三个 Tab，和任务模块零耦合**：

- 任务屏不因为记账变复杂（还是那两栏，一个字没改）
- 记账屏也不受「减少判断」那条约束的管辖（记账本来就该允许你补记、允许你改）

**两个模块各自保持纯粹，拼在同一个 App 里但互不干涉。** 表也是两张，谁也不因为对方而多一个字段。

> 顺带一个判断：这次记账**只记支出**，不记收入。你提的需求是「每日总花了多少每周每月」——
> 把支出记准，就已经回答了这个问题；加上收入会把界面变成一张收支表，那就不是这个 App 该管的事了。

## v0.4：记账从「今天」长到「这几个月」

v0.3 的记账屏只能看**当天**，看历史得一天一天点「←」。想回看 9 月 3 日，要点四十次。

这不是「少个功能」，是**这个面根本没为长期使用做准备** —— 一个翻不了往事的账本只回答「今天花了多少」，而记账真正的价值在「这段时间我花哪去了」。

v0.4 加的是**层级**，不是统计：

| 看哪一层 | 回答什么 | 在哪看 |
|---|---|---|
| 今日 / 本周 / 本月 | **此刻**花了多少 | 「记一笔」抬头的大数字 |
| 月历 | 这个月**每天**花了多少 | 「看花销」的整月格子 |
| 明细 | **那天**每一笔是什么 | 点月历某天，落到明细上 |

三层各答一个问题，不重复。

刻意**没有做分类统计**（餐饮 / 交通各占多少）—— 那要求每一笔都打标签，而「每笔都要打标签」的成本，会让人干脆停止记账。

**四个设计上的决定：**

**1. 格子里的深浅是「相对这个月」，不是绝对值。**
一顿 100 块的饭，在月消费 300 的月份里是大头，在月消费 8000 的月份里不算什么。所以深浅拿当天去除以本月峰值 —— 它回答的是「这个月哪几天花得特别多」，而不是「这天绝对花了多少」。

**2. 不改数据库结构。**
按日聚合就是 `GROUP BY date` 一句 SQL，不新增表、不新增字段。所以 `AppDatabase` **仍然是 version 2，没有新迁移，覆盖安装零风险**。
这是刻意的：能靠查询解决的事，不去动结构 —— 动结构的代价是你要么写迁移、要么可能丢数据。

**3. 文字一律深色，深浅只做在底色上。**
如果改成「底色深就换白字」，白字要够对比度就得把底色压到几乎全蓝，档位之间的差别反而没了 —— 而档位分不开，月历就白做了。现在 4 档底色下深字的对比度都在 5.5:1 以上。

**4. 顶部那行灰字锚定真正的今天，不跟着月份走。**
翻到 3 月时，如果「今日 / 本周 / 本月」也跟着变成 3 月，那「今天花了多少」就永远看不到了。所以月历下面的「合计」是你**正在看的那个月**，顶上那三列是**此刻** —— 两个时间维度，用颜色分出主次。

## v0.5：把「记账」这一步本身做短

到 v0.4 为止，账本能翻、能看分布，但**记一笔还是很麻烦**。一次完整的记账是这样的：

```
切 Tab → 点金额框（弹数字键盘）→ 输 32 → 点备注框（键盘切成中文）→ 输「午饭」→ 点「记一笔」
```

六次动作、两次键盘类型切换。真正拖时间的不是输数字，是**两个框之间的跳转**和**输入法切换**。

### 解法：把「打字」换成「点选」

记账的真实分布是**少数名目反复出现** —— 午饭、通勤、咖啡。所以备注不该每次都重新打一遍：

```
  午饭  咖啡  地铁  打车  超市  + 自己写
┌────────────────────────────────────┐
│  ¥ 32                        ( 记 ) │
└────────────────────────────────────┘
```

- 标签来自**历史账目的频率统计**（`GROUP BY note`，取前 8），用户一次都不用维护
- 主路径变成：点标签 → 输数字 → 点「记」，**全程数字键盘，零输入法切换**
- 再点一次标签可以取消 —— 选中态本身要能表达「这一笔不写备注」
- 想写新备注才点「+ 自己写」，展开一个输入框并自动聚焦

**关键：标签不是分类体系。** 它只是把常用备注抬到一键，不做统计、不做占比、不新增表 —— 所以也不会有「每笔都要打标签」的成本。这条线划得很清楚：v0.4 拒绝的分类统计还是拒绝，v0.5 只是让没被拒绝的那部分变快。

### 界面上的六处改动

| # | 原来 | 现在 | 为什么 |
|---|---|---|---|
| 1 | 两个带框输入框并排 + 右下角文字按钮 | 一整条底部栏：大号金额 + 圆形「记」 | 原来的样子像一张要填的表，视觉重心散在三处 |
| 2 | 「记在 今天」常驻一行 | 并进日期导航：`← 今天 · 10/21 →` | 那行永远在、永远说同一件事，白占一行高度 |
| 3 | 每行右侧常驻「×」删除 | 删除收进编辑态（`✓` / `删` / `×`） | **账目删除不可撤销**，常驻「×」正好在手指落点上 |
| 4 | 空态文案贴左 | 居中 + 一行引导 | 贴左的一行字看起来像「列表到此为止」，而不是「这里是空的」 |
| 5 | 「记一笔 / 看花销」是带下划线的文字 | 两格分段控件 | 原来和顶部三栏长得几乎一样，层级糊在一起 |
| 6 | 今日/本周/本月挤一行 13sp | 三列小网格，今日用主色 | 一行放不下就截断，而这恰好是最想说的东西之一 |

第 3 项不是审美问题，是数据安全问题。为了省一次点击，把「误删一笔账」的概率铺在每一行、每一屏上，不划算。

## v0.6：颜色变成一套、背景可以换、标签归自己、多一个日记

### 一、「颜色统一」统一的是什么

v0.5 之前是两套写死的色值：浅色档蓝灰、深色档无彩深灰。切 Tab 时不是明暗变化，是**换了个色系** —— 从蓝跳到灰，像两个 App 拼在一起。

v0.6 把颜色收成一套 `Palette`：一个主题就是一组语义色值，换主题不再改代码。

| | v0.5 | v0.6.1 |
|---|---|---|
| 换主色 | 改 `Color.kt` 重新编译 | 设置里点一下，立刻生效 |
| 切 Tab | 蓝色 → 灰色（换色系） | **背景色完全一致，不跳** |
| 规划屏 | 永远是无彩深灰 | 跟其余三个面同一底色 |

五套预设：**靛蓝 / 墨绿 / 赭石 / 藕粉 / 岩灰**。

**为什么不做「自选任意颜色」**：好看在于配色是调出来的，不是算出来的。开放调色盘，派生色会有一半达不到对比度 —— 到时候界面上会出现读不清的字，而用户不知道为什么。这五套的主色都是手工压过亮度的。

**为什么最初规划屏是深色，后来又不是了**：v0.6 留了明度差，理由是睡前低刺激。用过之后发现那个理由站不住 —— 四个 Tab 里三个是浅的，只有规划屏整屏翻黑，切过去像进了另一个 App。**一个「统一」的界面里不该有一个例外，哪怕那个例外有道理。** v0.6.1 把这一档撤掉，四个 Tab 背景完全一致。

v0.7 又把深档请回来了，但换了个判断依据：**不再是「你在哪一屏」，而是「你自己要不要」**。顶栏一个 ☾，按一下四屏同时暗，再按一下同时亮。同一件事，按屏幕自动切换是打扰，按用户手动切换是尊重 —— 差别不在深色本身，在谁做决定。

### 二、背景图

从相册选一张，铺在**所有** Tab 下面。

三个实现上的取舍：

1. **一定要压遮罩**（默认 α 0.88，可在设置里调）。任何一张照片的明暗分布都是随机的，不压一层背景色，正文对比度就没法保证。
2. **每个 Tab 都铺**。既然是「统一」，就不能有一屏偷偷用纯色。
3. **图片存私有目录、库里只存文件名**。绝对路径里带包名和用户 id，换设备或恢复备份必然失效。

选图走系统 Photo Picker，**不需要任何存储权限**。

清晰度可调（v0.8）：设置里一根滑杆，遮罩 0.75（最清楚）～ 0.96（最淡），默认 0.88；夜间自动再厚一档（+0.05）。同时把导入分辨率从 1600 提到 **2560** —— 背景是 `ContentScale.Crop` 铺满屏幕的，1600 长边的图铺 1080×2400 竖屏要放大 2 倍，只调遮罩救不回来。详见「v0.8：背景清晰度」。

### 三、标签从「算法统计」改成「自己的」

v0.5 的标签是从历史备注里按频率算出来的前 8 个。v0.6 按你的要求改掉：

- 内置 8 个：午饭 / 早饭 / 晚饭 / 咖啡 / 地铁 / 打车 / 超市 / 房租
- 「+ 自己写」旁边多一个「**存为标签**」，写一次就能永久留下
- 长按任意标签 → 管理面板：删、加

**存哪里：SharedPreferences 一段 JSON，不建表。**
标签是配置，不是账目数据。建表就要写迁移，而迁移是本工程唯一可能丢数据的动作 —— 为了存几个字符串去动账本结构，代价和收益不成比例。配置坏了最多丢标签，账本永远完好。

**删标签不删账**：账目里存的始终是备注文本，标签只是往那个框里填字的快捷方式。这句话也写在了管理面板里。

### 四、日记

第四个面。**一天一篇**，`date` 直接做主键。

| 有什么 | 没有什么 |
|---|---|
| 多行正文，不限长度 | 分类 |
| 心情 5 档（可空，再点一次取消） | 标签 |
| 配图 1 张 | 搜索 |
| 停笔 800ms 自动保存 | 「保存」按钮 |

最后一条是关键：写日记时手一停就要点一次保存，那个动作本身就打断思路。这里改成自动存 —— 用户永远不用想「存了没」。

翻页前会先把手上这篇落盘再走，否则「写完马上翻走」会丢最后 800ms 的内容。

**这是本工程第一次真正新增第二张表**：`AppDatabase` 从 v2 升到 v3，手写 `MIGRATION_2_3`。前几版之所以能一直不动结构，是因为月历和标签都能靠查询解决；日记是全新的数据类型，绕不过去。

## v0.7：夜间模式

顶栏右上角，一个 ☾。按一下四屏一起暗，再按一下一起亮，状态存在本机。

### 为什么它该常驻在顶栏

因为它天天要用，而且用的时机很具体 —— **「现在这一刻光线不对」**。那一刻再去切设置、找到开关、切回来，光已经不对了。所以它宁可和「设置」并排放着，占掉顶栏一小块位置。

代价是顶栏本来就满：四个 Tab 加两个入口。实测一个符号宽度的挤压，比每次多跳两次值得。

### 一个符号，两种亮度

符号永远是月亮，**不会变成太阳**。

如果跟着状态换图标，用户每次都要先想一遍「这个太阳是表示现在是白天，还是表示点一下会变成白天」—— 这题没有标准答案，两种设计都有人用。所以干脆不换：灰月亮 = 关，主色月亮 + 一圈淡主色底 = 开。像手电筒按钮，一看就懂。

### 三处会被「底色反转」带偏的地方

加一个夜间模式，真正的工作量不在配色，在这三处：

| 位置 | 会怎么坏 | 处理 |
|---|---|---|
| **状态栏图标** | `enableEdgeToEdge()` 默认按**系统**深色设置决定图标黑白，和 App 内开关不同步 —— 系统浅色 + App 夜间时，那排深色图标整个消失在深底上 | 手动按开关设 `isAppearanceLightStatusBars` |
| **月历格子** | 如果字色写死「深色」，夜间档整屏看不见数字 | 字色一律取 `onBackground`，由主题在两端各配一次 |
| **设置里的色点** | 一直显示浅档的主色，而夜间实际用的是提亮过的那一档，选完发现颜色对不上 | 色点跟随当前模式显示 |

第一项最容易被漏掉，因为编译能过、界面能开、只有状态栏那一行是空的。

### 背景图在夜里怎么办

**照铺，只是在用户选的基础上再加厚 0.05。**

换个方向做（夜间干脆不铺图）更省事，但那就又给夜间开了个例外 —— 和 v0.6.1 刚收掉的那个毛病是同一个。用户调到最淡（0.96）时加厚会被截住，退化成日夜一样，不报错。

### 不跟随系统深色模式

系统的深色设置管整个手机，这个开关只管这四个 Tab。两个口径混在一起，就会出现「我明明关掉了它却还是黑的」，而用户找不到原因。所以：**明暗只有一个判断者，就是这个开关。**

## v0.8：背景清晰度

需求原话是「把背景的清晰度变成可调节的」。第一版方案只做了一件事——加一根控制遮罩浓度的滑杆——翻代码时发现漏了更重要的一半。

### 不清有两个原因，滑杆只能修一个

| 原因 | v0.7 的状况 | 后果 |
|---|---|---|
| **遮罩太厚** | 固定 0.88，图只剩 12% 透出来 | 图被压没了 |
| **分辨率不够** | 导入时长边压到 1600px | 图被放大 2 倍，边缘发软 |

背景图是 `ContentScale.Crop` 铺满整屏的。要铺满 1080×2400 的竖屏，一张 4:3 横图的**高**必须 ≥ 2400，也就是长边 ≥ 3200；1600 长边的图高只有 1200，等于放大 2 倍去看。**所以只调遮罩，拉到最清楚也还是糊。**

两个都改了：遮罩可调，导入分辨率 1600 → **2560**（图高 1920，放大约 1.25 倍，肉眼基本看不出插值）。内存从 7.3MB 涨到 18.7MB，一张全屏背景换这个清晰度，值。

### 滑杆的四个决定

1. **范围 0.75 ～ 0.96，默认 0.88。** 下限 0.75 是「图透出四分之一、显著但正文会发灰」的位置；再往下就该直接点「移除」了。默认值精确对齐 v0.7，装完不动的话看起来一模一样。
2. **一个滑杆，日夜联动。** 用户要表达的只有一句「图该清楚到什么程度」，夜里自动退一档就够了。做两个滑杆等于让同一件事理解两遍。
3. **存的是遮罩 alpha，不是「清晰度百分比」。** 真正生效的就是它，`prefs` 里看到 0.88 就知道是什么，不用反推。滑杆方向与遮罩反向（往右拖 = alpha 变小 = 图更清楚），这个换算只出现在 `ClaritySlider` 一处。
4. **不显示百分比，显示「偏淡 / 适中 / 清楚」。** 百分比会被读成「清晰度只有 38%」，而真实含义是「遮罩浓度 88%」——那种数字只会让人想凑个整。

### 旧图不会自动变清晰

分辨率是**导入那一刻**定下的。改 `MAX_DIMEN` 只影响以后新选的图，已经存下的 1600px 文件不会变。设置里写了一句实话：「以前选过的图是按较低分辨率存的，觉得糊就重新选一次。」

### 四个面 + 一个设置，同一个背景色

- **今天 / 规划 / 记账 / 日记** 四个面底色永远一致
- **设置**不占 Tab：Tab 是内容，设置是配置

明暗由**顶栏那个月亮**决定，四屏同时变。它不跟随系统深色模式，也不按 Tab 自动切 —— 曾经按 Tab 切过（v0.6 的规划屏），结果是四个面里只有它翻黑，切过去像进了另一个 App。

**色系是跟着主题走的**：换一个主题色，五个面同时变。色系和明暗是两个维度，互不干扰。

### 两个小决定

**勾完不倒着往下沉。** 清单的位置就是你排的位置，勾选不会让列表跳动。列表自己会跳的界面，人是记不住自己排的顺序的。

**复选框是双向的。** 勾上是完成，再点一下退回待做。勾错了没得救的清单，用两次就不敢用了。

## 记账的几个决定

**1. 汇总卡锚定「真正的今天」，不跟着明细往回翻。**
明细可以一直往回走去看历史，但顶部那张卡永远算的是**今天 / 本周 / 本月**。
如果卡片跟着明细走，翻到上周三时它会变成「上周三 / 那一周 / 那个月」—— 三个数字全换了意思，而你以为自己看的是「我今天花了多少」。这是最容易被忽略、但一定会踩的一个坑。

**2. 不能翻到未来。**
未来的账不存在，能翻过去只会让人怀疑数据。所以日视图的「→」到今天就到底，月视图的「→」到当月就到底。

**3. 日期导航就是输入日期，备注优先给标签。**
「`← 今天 · 10/21 →`」那一行的日期，同时也是你这一笔记在哪天 ——
所以**补记不需要再选一次日期**，往回翻一天直接写就行。
备注则优先点标签（内置八个，自己存的会一直留着），
偶尔要写新的才点「+ 自己写」—— 需要打字是例外，不是常态。

**4. 金额一律用整数存（单位「分」）。**
`Double` 表示不了 0.1，二进制浮点累加到月总额就会和实际对不上。所以数据库、领域模型、聚合 SQL 全程是 `Long` 的「分」，**只有输入和显示两个端点才出现「元」**。这条约束在代码里是一路贯穿的，不是只写在数据库那一层。

**5. 输入看不懂就说看不懂，不猜。**
`32`、`32.5`、`32.50` 都收；`32.567`、`abc`、负数一律拒绝并提示。
刻意不做「悄悄四舍五入成 32.57」这种事 —— 账本上最不该有的就是系统替你改过的数字。

**6. 删除是真删，不是打标记 —— 但入口藏进了编辑态。**
账记错了就是记错了。留一堆看不见的墓碑，只会让「本月合计」和明细对不上时更难查。
既然是真删、不可撤销，那它就不该是一个常驻在每行右边、正好落在手指上的「×」。
现在要删一笔：先点开那一行，再点「删」。多一次点击，换掉「手滑就没了一笔账」。

**7. 周和月的边界是人在过的日子。**
本周 = **周一 00:00 起**（不是周日），本月 = 1 号到月末。理由是发工资、还信用卡、看账单的周期都是周一，
「本周花了多少」必须和你脑子里的那个「本周」是同一个区间 —— 否则数字对上了，直觉对不上。
月历的第一列同样放**周一**，不然「本周」和月历上的行对不上。

**8. 月历格子里的金额只到「元」，上千用 k。**
一格只有 44dp 宽，`¥128.50` 塞不进去。丢掉的分只影响这一个格子的观感 ——
合计和明细仍然精确到分。月历是拿来看分布的，不是拿来对账的；对账有明细和汇总。

### 几个关键设计

**1. 三张表，各管各的**
`tasks` / `expenses` / `journal` 是三张独立的表，不 join、不互相引用。UI 只认 `Task` / `Expense` / `Journal` 三个领域模型，Room 的 Entity 封在 Repository 内部。
换存储引擎、加云同步，UI 一行不用改。

唯一共享的东西是「日期」这个字符串的格式（`yyyy-MM-dd`）—— 这让「某一天都发生了什么」将来可以靠三次独立查询拼出来，而不必现在就把三张表绑死。

**2. 全链路 Flow**
Room 数据一变，界面自动刷新。记完一笔，三个合计和当前月历由各自独立的聚合查询重算 —— 没有手动 `refresh()`，也没有缓存的合计。

**3. 月历的聚合交给 SQLite，不捞回内存再分组**
月历只要 31 个数字，没必要为它把整月明细查上来。账本是「只增不减」的数据，一年就是几千行 —— 这个区别会逐年变明显。

**4. 调序是「按位重写」，不是「交换两条」**
上移 / 下移时把当天的清单整段重写成 `1..n`，而不是只交换相邻两条的 `orderIndex`。
历史数据里 `orderIndex` 有可能重复（两次 `add` 撞上同一个 `max` 时就会），交换只会把重复值原样留下；逐位重写才能保证序列一直是干净的。

**5. 行内动作不用图标库**
`↑ ↓ × ✓ ← →` 几个字符就够用，省下一个依赖和一堆矢量资源。同时因为它是 `Text` 而不是 `IconButton`，尺寸小、不抢注意力 —— 一行里的次要动作不该长得比内容还显眼。

**6. 依赖只有一条链，不引额外框架**
没引入 Hilt、没引入 Navigation、没引入图表库。屏幕只有三个、依赖链只有一条，引库的收益接近零、成本是一层抽象。这个判断写在代码注释里。

## 关于数据库升级

| 版本 | `AppDatabase.version` | 迁移 |
|---|---|---|
| v0.1 | 1 | —（首发） |
| v0.2 | 1 | **无迁移**。刻意没动表结构，覆盖安装即可，数据全部保留 |
| v0.3 | 2 | **有迁移** `MIGRATION_1_2`：只新增 `expenses` 表，`tasks` 表一个字段都没碰 |
| v0.4 | 2 | **无迁移**。月历是纯查询（`GROUP BY date`），不新增表、不新增字段 |
| v0.5 | 2 | **无迁移**。常用标签也是纯查询（`GROUP BY note`），同样不新增表、不新增字段 |
| v0.6 | 3 | **有迁移** `MIGRATION_2_3`：只新增 `journal` 表，`tasks` / `expenses` 一个字段都没碰。同时删掉了 v0.5 的标签统计 —— 标签改存 SharedPreferences，不进库 |
| v0.6.1 | 3 | **无迁移**。只改了主题层（去掉 `night` 参数），不动任何表和字段 |
| v0.7 | 3 | **无迁移**。夜间开关存 SharedPreferences（`night_mode`），不进库 |
| v0.8 | 3 | **无迁移**。清晰度存 SharedPreferences（`bg_dim`）；改的是图片导入分辨率，那本来就不进库 |

这五次「无迁移」不是巧合，是设计时第一个要想的问题：**这件事能不能不动结构就做完？**
能不动，安装风险就是零 —— 不用赌迁移写对没写对。

关于 v0.3 那次真迁移，有一点值得说清楚：

- 如果迁移 SQL 与 Room 期望的结构不一致，Room 会在**打开数据库时直接抛异常、App 闪退** ——
  问题当场暴露，而**数据库文件是完好的，数据还在**。
- 真正会导致**静默清库**的只有 `fallbackToDestructiveMigration()`（结构对不上就把库删了重建）。
  **本工程从头到尾没有用它，也不打算用。** 宁可崩给你看，也不能悄悄清掉你的账。

`app/schemas/` 目录是 Room 导出的**结构基准**（由 KSP 生成，已提交进仓库）。
写迁移 SQL 时必须逐字对照它 —— 这是在**没有模拟器的机器上**唯一能自证「迁移结果与 Entity 期望一致」的手段。
反过来它也有一项用处：**没生成新的 schema 文件，就等于机器确认了「这一版没动结构」。**

## 已知边界（v0.8）

| 限制 | 说明 |
|---|---|
| **没有数据导出** | **这是目前最明显的缺口**，见下方。现在有三类数据了（任务 / 账目 / 日记），丢的代价又翻了一倍 |

### 关于数据安全

数据全在本机，**卸载 App 会全部丢失** —— 任务、账目、日记、图片、主题设置，一个不剩。
在加上「导出」功能之前，重要内容请自己另外记一份。
这是下一步的第一优先项 —— 它是唯一的后悔药。**而且现在数据从两类变成了三类。**

1. **数据导出**（最该先做）—— 唯一的后悔药，而且要同时覆盖任务、账目、日记和图片
2. **早上提醒** —— 涉及通知权限与国产 ROM 白名单引导
3. **任务的历史回顾** —— 账目能翻月份了，任务这边还没有
4. **日记的时间线** —— `JournalDao.observeTimeline()` 已经写好了，缺的是一个列表页
5. **任务拆解** —— 把「写周报」变成「打开上周周报，三个项目各写一行」
   这是把判断力消耗真正降到零的那一步，也是最值得接入 AI 的位置
6. **桌面快捷入口** —— 长按「今晚」图标直接进某一屏（静态 App Shortcuts，零权限）
7. **连续记账** —— 记完不收起键盘、不清焦点，一次把一天的账补完

## 技术栈版本

版本集中在 `gradle/libs.versions.toml`（Version Catalog），改版本只需动这一个文件：

```
AGP 8.7.3 · Kotlin 2.0.21 · Compose BOM 2024.11.00 · Room 2.6.1
```

若你的 Android Studio 要求更高的 AGP，直接改此文件即可，其他文件不用动。
