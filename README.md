# 今晚

> 今晚排好，明天照着做。

一个每日便签：**在你想规划的时候把要做的事写下来，第二天打开就是一份可以随手勾掉的清单。**

- 平台：Android（`minSdk 26` / `targetSdk 35`）
- 技术：Kotlin + Jetpack Compose + Room
- 数据：纯本地存储，**无账号、无联网、无数据收集**
- 状态：v0.2，已编译验证（见「验证记录」）

---

## 为什么做这个

大多数待办 App 的逻辑是「帮你记住」。但真正消耗人的不是「记不住」，而是「**不知道该先做哪个**」。

于是它们给你列表、优先级、进度条 —— 让你在动手之前先做一轮排序决策。

这里想做的事正相反：**把「决定做什么、按什么顺序」提前到你精力还够的时候做完，第二天早上不用再想。**

---

## 从 v0.1 到 v0.2：三条硬规则的复盘

v0.1 为了把判断力消耗压到最低，定了三条硬规则：早上**只显示一件事**、一天**最多 5 件**、规划完**就结束**。

自己用了一周之后，三条全部出了问题 —— 不是理念错，是**手段太硬**：

| v0.1 的规则 | 真实使用中发生的事 |
|---|---|
| 早上只给一件事 | 排第一的那件暂时做不了（要等人回消息、环境没准备好），整天就卡死在那里，没有任何跳过的入口 |
| 一天最多 5 件 | 上限校验写成了「全部条数」而不是「未完成条数」—— 删掉一条想换一条，就再也加不回来了 |
| 规划完就结束 | 点完「就这样」停在一句「晚安」上，当天想再补一件事也进不去，只能杀掉 App |
| 计划写完不能改 | 错字、顺序不对、不想做了 —— 全都没办法 |

**这些不是理念错了，是把手段当成了目的。**

「不给选择」是手段，目的是「不消耗判断力」。而当手段本身开始消耗判断力 —— 还得记着别踩上限、还得祈祷第一件能做、还得担心写错一个字就废了 —— 它就从帮手变成了负担。

于是 v0.2 把三处硬规则拆掉，换成：

| 原来 | 现在 | 有意保留的是什么 |
|---|---|---|
| 只给一件 | 给完整清单，**任意顺序勾选** | 顺序仍是你自己排的，界面不做二次排序 |
| 最多 5 件 | **没有上限** | —— |
| 规划完就结束 | 顶部「今天 / 规划」**两个 Tab 随时互达** | 两个面气质不同：白天浅色，夜里深色 |
| 计划不能改 | 可改文字、可调顺序、可删除、可取消勾选 | —— |

一句话概括：**v0.1 帮你把决定做完，v0.2 允许你改主意。**

## 快速开始

### 方式 A：Android Studio（推荐）

1. Android Studio → **Open** → 选中本仓库根目录
2. 等待右下角 Gradle Sync 完成（首次会下载依赖）
3. 连接手机（开启「开发者选项 → USB 调试」），点绿色三角 Run

> 若提示缺少 SDK 组件，点提示里的安装即可。本项目在
> **Android SDK Platform 35** + **Build-Tools 34.0.0** 上编译通过。

### 方式 B：命令行（从仓库根目录执行）

```bash
# JDK 需 17+；Android Studio 自带的 JBR 即可
export JAVA_HOME="$LOCALAPPDATA/Programs/Android Studio/jbr"   # 路径按本机实际情况调整
export ANDROID_HOME="$LOCALAPPDATA/Android/Sdk"

./gradlew :app:assembleDebug
```

产物与安装：

```bash
# 产物
app/build/outputs/apk/debug/app-debug.apk

# 装到手机（USB 调试已开启）
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

> 也可以直接把 `app-debug.apk` 传到手机上点击安装（需允许「安装未知应用」）。

## 日常怎么用

| 时间 | 你做什么 | App 做什么 |
|---|---|---|
| 睡前 / 任何想规划的时候 | 切到「规划」，写下要做的事 | 深色界面，安静地收下 |
| 第二天 | 打开，默认落在「今天」 | 一份清单，随手勾 |
| 做着做着 | 想到新的事、想改一条 | 切到「规划」，改文字 / 挪顺序 / 删掉都行 |
| 全勾完 | — | 清单底部一句「今天就这样。」 |

### 两个 Tab，两种气质

- **今天**是浅色：白天，要一眼看清
- **规划**是深色：睡前低刺激

这两套主题是**写死的，不跟随系统深色模式**。因为深浅色在这里是功能，不是偏好 —— 若跟随系统，一个开着浅色模式的用户晚上会看到刺眼白屏，产品意图直接破功。

切换 Tab 时整屏会由浅转深（或反过来）。这个跳变是有意的：白天和夜里本来就该是两种气质。

### 两个小决定

**勾完不倒着往下沉。** 清单的位置就是你排的位置，勾选不会让列表跳动。列表自己会跳的界面，人是记不住自己排的顺序的。

**复选框是双向的。** 勾上是完成，再点一下退回待做。勾错了没得救的清单，用两次就不敢用了。

## 项目结构

```
app/src/main/java/com/clivena/tonight/
├── MainActivity.kt              入口 + 两个 Tab 的路由
├── MainViewModel.kt             决定打开时落在哪个 Tab
├── TonightApp.kt                手动持有依赖（未引入 Hilt）
├── data/
│   ├── TaskRepository.kt            接口 —— 数据层对 UI 的唯一出口
│   ├── LocalTaskRepository.kt       本地实现
│   └── local/                       Room：Entity / Dao / Database
├── domain/Task.kt               领域模型（UI 只认这个）
├── ui/
│   ├── theme/                   两套硬绑定的主题
│   ├── components/TopTabs.kt    「今天 / 规划」切换栏
│   ├── today/                   今天屏：清单 + 任意勾选
│   └── plan/                    规划屏：增 / 删 / 改 / 排序
└── util/DateUtil.kt             日期归属与显示
```

### 几个关键设计

**1. 只有一张表，但预留了同步字段**
`TaskEntity` 一张表存全部。不建「计划表」—— 日期可以从 `planDate` 派生，多一张表就多一层 join 和一致性维护。
但预先建好了 `remoteId` / `updatedAt` 两个空字段，**将来接云同步零迁移成本**（Room 加字段要写 Migration）。

**2. UI 层不碰 Room 类型**
UI 只认 `Task`（domain 模型），`TaskEntity` 封在 Repository 内部。换存储引擎、加云同步，UI 一行不用改。

**3. 全链路 Flow**
Room 数据一变，界面自动刷新。没有手动 `refresh()`。

**4. 调序是「按位重写」，不是「交换两条」**
上移/下移时把当天的清单整段重写成 `1..n`，而不是只交换相邻两条的 `orderIndex`。
历史数据里 `orderIndex` 有可能重复（两次 `add` 撞上同一个 `max` 时就会），交换只会把重复值原样留下；逐位重写才能保证序列一直是干净的。

**5. 没有条数上限**
v0.1 把它当成核心约束写在 Repository 里，v0.2 删掉了。理由见上面的复盘 —— 当约束开始消耗判断力（记着还剩几个名额），它就已经违背了自己的目的。

**6. 依赖只有一条链，不引额外框架**
没引入 Hilt、没引入 Navigation。屏幕只有两个、依赖链只有一条，引库的收益接近零、成本是一层抽象。这个判断写在代码注释里。

## 已知边界（v0.2）

| 限制 | 说明 |
|---|---|
| **没有数据导出** | **这是目前最明显的缺口**，见下方 |
| 没有提醒 | 需要通知权限 + 国产 ROM 后台保活 |
| 不能跨天挪任务 | 今天没做的不能一键挪到明天，只能自己重写一条 —— 刻意不做，那会让「哪天做什么」变得可以随意篡改 |
| 没有历史回顾 | 数据都在，只是没有界面 |
| 跨天不自动刷新 | App 长期驻留后台跨过零点时，需重启一次 |

### 关于数据安全

数据全在本机，**卸载 App 会全部丢失**。
在加上「导出」功能之前，重要内容请自己另外记一份。
这是下一步的第一优先项 —— 它是唯一的后悔药。
