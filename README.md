# 今晚

> 今晚排好，明天照着做。

一个每日便签：**在你想规划的时候把要做的事写下来，第二天打开就是一份可以随手勾掉的清单。**

v0.3 起多了一个**独立的「记账」面**；v0.4 给这个面加了**月历**；v0.5 把记账的输入从「打字」改成「点标签」。
v0.6 是三件事一起做：**主题可以换**（五套配色）、**自定义背景图**、**标签变成自己的**，以及新增的第四个面 —— **日记**。
v0.6.1 把最后一个不统一的地方收掉：四个 Tab 背景色完全一致。
v0.7 把深色还回来，但这次是**你自己按的** —— 顶栏一个月亮，四屏同时变暗。
v0.8 让背景图可以调清楚：一根滑杆控遮罩浓度，同时把图片的导入分辨率从 1600 提到 2560 —— 后一件才是「图糊」的真正原因。
v0.9 补上了这个项目欠了十几版的那件事：**数据导出**。一个 zip 里装着能读回去的 `data.json`、给人看的三个 csv，以及配图 —— 换手机时「从备份恢复」就搬过去了，而且是**合并**，不会删掉你在新手机上已经记的内容。
v0.10 把「背景图上面永远有一层膜」这件事彻底解决：滑杆能拖到 **0**，屏幕上只剩那张图。字由内容自己的一块半透明圆角底托住，不再靠全屏遮罩。
v0.11 把桌面小组件搬上来：一张 4×2 的卡，左边是今天要做的、右边是今天花了多少。第一版装上去显示「载入窗口小插件时出现问题」—— 原因是一个 `<View>` 标签，详见「验证记录」。
v0.12 把桌面小组件做成四种规格：**4×2 / 5×2** 是一半待办一半记账，**3×2** 只有待办、**2×2** 只有记账。想要哪一块，就把哪一块单独搬上桌面。
v0.13 给日记加了**日历**：哪些天写过一眼看完，点一下就到。找上周那篇不用再按七次「←」。

- 平台：Android（`minSdk 26` / `targetSdk 35`）
- 技术：Kotlin + Jetpack Compose + Room
- 数据：纯本地存储，**无账号、无联网、无数据收集**，**零运行时第三方依赖**，`uses-permission` 一条都没有
- 状态：v0.13.0，已编译验证 + 10 个单元测试 + 三条自证脚本（见「验证记录」）

## 为什么做这个

大多数待办 App 的逻辑是「帮你记住」。但真正消耗人的不是「记不住」，而是「**不知道该先做哪个**」。

于是它们给你列表、优先级、进度条 —— 让你在动手之前先做一轮排序决策。

这里想做的事正相反：**把「决定做什么、按什么顺序」提前到你精力还够的时候做完，第二天早上不用再想。**

## 从 v0.1 到 v0.2：三条硬规则的复盘

v0.1 为了把判断力消耗压到最低，定了三条硬规则：早上**只显示一件事**、一天**最多 5 件**、规划完**就结束**。

自己用了一周之后，三条全部出了问题 —— 不是理念错，是**手段太硬**：

| v0.1 的规则 | 真实使用中发生的事 |
|---|---|
| 早上只给一件事 | 排第一的那件暂时做不了（要等人回消息、环境没准备好），整天就卡死在那里，没有任何跳过的入口 |
| 一天最多 5 件 | 上限校验写成了「全部条数」而不是「未完成条数」—— 删掉一条想换一条，就再也加不回来了 |
| 规划完就结束 | 点完「就这样」停在一句「晚安」上，当天想再补一件事也进不去，只能杀掉 App |
| 计划写完不能改 | 错字、顺序不对、不想做了 —— 全都没办法 |

**这些不是理念错了，是把手段当成了目的。**

「不给选择」是手段，目的是「不消耗判断力」。而当手段本身开始消耗判断力 —— 还得记着别踩上限、还得祈祷第一件能做、还得担心写错一个字就废了 —— 它就从帮手变成了负担。

于是 v0.2 把三处硬规则拆掉，换成：

| 原来 | 现在 | 有意保留的是什么 |
|---|---|---|
| 只给一件 | 给完整清单，**任意顺序勾选** | 顺序仍是你自己排的，界面不做二次排序 |
| 最多 5 件 | **没有上限** | —— |
| 规划完就结束 | 顶部「今天 / 规划」**两个 Tab 随时互达** | 不用退出重进，规划是随时能回去改的 |
| 计划不能改 | 可改文字、可调顺序、可删除、可取消勾选 | —— |

一句话概括：**v0.1 帮你把决定做完，v0.2 允许你改主意。**

## v0.3：为什么记账是「另一个 Tab」

这个 App 从立项起就写了一条硬规则：**不做统计、不做分类标签**。因为这些东西都在增加判断力消耗。

而记账天生就是统计。所以 v0.3 没有把记账揉进任务流里，而是**把它做成第三个 Tab，和任务模块零耦合**：

- 任务屏不因为记账变复杂（还是那两栏，一个字没改）
- 记账屏也不受「减少判断」那条约束的管辖（记账本来就该允许你补记、允许你改）

**两个模块各自保持纯粹，拼在同一个 App 里但互不干涉。** 表也是两张，谁也不因为对方而多一个字段。

> 顺带一个判断：这次记账**只记支出**，不记收入。你提的需求是「每日总花了多少每周每月」——
> 把支出记准，就已经回答了这个问题；加上收入会把界面变成一张收支表，那就不是这个 App 该管的事了。

## v0.4：记账从「今天」长到「这几个月」

v0.3 的记账屏只能看**当天**，看历史得一天一天点「←」。想回看 9 月 3 日，要点四十次。

这不是「少个功能」，是**这个面根本没为长期使用做准备** —— 一个翻不了往事的账本只回答「今天花了多少」，而记账真正的价值在「这段时间我花哪去了」。

v0.4 加的是**层级**，不是统计：

| 看哪一层 | 回答什么 | 在哪看 |
|---|---|---|
| 今日 / 本周 / 本月 | **此刻**花了多少 | 「记一笔」抬头的大数字 |
| 月历 | 这个月**每天**花了多少 | 「看花销」的整月格子 |
| 明细 | **那天**每一笔是什么 | 点月历某天，落到明细上 |

三层各答一个问题，不重复。

刻意**没有做分类统计**（餐饮 / 交通各占多少）—— 那要求每一笔都打标签，而「每笔都要打标签」的成本，会让人干脆停止记账。

**四个设计上的决定：**

**1. 格子里的深浅是「相对这个月」，不是绝对值。**
一顿 100 块的饭，在月消费 300 的月份里是大头，在月消费 8000 的月份里不算什么。所以深浅拿当天去除以本月峰值 —— 它回答的是「这个月哪几天花得特别多」，而不是「这天绝对花了多少」。

**2. 不改数据库结构。**
按日聚合就是 `GROUP BY date` 一句 SQL，不新增表、不新增字段。所以 `AppDatabase` **仍然是 version 2，没有新迁移，覆盖安装零风险**。
这是刻意的：能靠查询解决的事，不去动结构 —— 动结构的代价是你要么写迁移、要么可能丢数据。

**3. 文字一律深色，深浅只做在底色上。**
如果改成「底色深就换白字」，白字要够对比度就得把底色压到几乎全蓝，档位之间的差别反而没了 —— 而档位分不开，月历就白做了。现在 4 档底色下深字的对比度都在 5.5:1 以上。

**4. 顶部那行灰字锚定真正的今天，不跟着月份走。**
翻到 3 月时，如果「今日 / 本周 / 本月」也跟着变成 3 月，那「今天花了多少」就永远看不到了。所以月历下面的「合计」是你**正在看的那个月**，顶上那三列是**此刻** —— 两个时间维度，用颜色分出主次。

## v0.5：把「记账」这一步本身做短

到 v0.4 为止，账本能翻、能看分布，但**记一笔还是很麻烦**。一次完整的记账是这样的：

```
切 Tab → 点金额框（弹数字键盘）→ 输 32 → 点备注框（键盘切成中文）→ 输「午饭」→ 点「记一笔」
```

六次动作、两次键盘类型切换。真正拖时间的不是输数字，是**两个框之间的跳转**和**输入法切换**。

### 解法：把「打字」换成「点选」

记账的真实分布是**少数名目反复出现** —— 午饭、通勤、咖啡。所以备注不该每次都重新打一遍：

```
  午饭  咖啡  地铁  打车  超市  + 自己写
┌────────────────────────────────────┐
│  ¥ 32                        ( 记 ) │
└────────────────────────────────────┘
```

- 标签来自**历史账目的频率统计**（`GROUP BY note`，取前 8），用户一次都不用维护
- 主路径变成：点标签 → 输数字 → 点「记」，**全程数字键盘，零输入法切换**
- 再点一次标签可以取消 —— 选中态本身要能表达「这一笔不写备注」
- 想写新备注才点「+ 自己写」，展开一个输入框并自动聚焦

**关键：标签不是分类体系。** 它只是把常用备注抬到一键，不做统计、不做占比、不新增表 —— 所以也不会有「每笔都要打标签」的成本。这条线划得很清楚：v0.4 拒绝的分类统计还是拒绝，v0.5 只是让没被拒绝的那部分变快。

### 界面上的六处改动

| # | 原来 | 现在 | 为什么 |
|---|---|---|---|
| 1 | 两个带框输入框并排 + 右下角文字按钮 | 一整条底部栏：大号金额 + 圆形「记」 | 原来的样子像一张要填的表，视觉重心散在三处 |
| 2 | 「记在 今天」常驻一行 | 并进日期导航：`← 今天 · 10/21 →` | 那行永远在、永远说同一件事，白占一行高度 |
| 3 | 每行右侧常驻「×」删除 | 删除收进编辑态（`✓` / `删` / `×`） | **账目删除不可撤销**，常驻「×」正好在手指落点上 |
| 4 | 空态文案贴左 | 居中 + 一行引导 | 贴左的一行字看起来像「列表到此为止」，而不是「这里是空的」 |
| 5 | 「记一笔 / 看花销」是带下划线的文字 | 两格分段控件 | 原来和顶部三栏长得几乎一样，层级糊在一起 |
| 6 | 今日/本周/本月挤一行 13sp | 三列小网格，今日用主色 | 一行放不下就截断，而这恰好是最想说的东西之一 |

第 3 项不是审美问题，是数据安全问题。为了省一次点击，把「误删一笔账」的概率铺在每一行、每一屏上，不划算。

## v0.6：颜色变成一套、背景可以换、标签归自己、多一个日记

### 一、「颜色统一」统一的是什么

v0.5 之前是两套写死的色值：浅色档蓝灰、深色档无彩深灰。切 Tab 时不是明暗变化，是**换了个色系** —— 从蓝跳到灰，像两个 App 拼在一起。

v0.6 把颜色收成一套 `Palette`：一个主题就是一组语义色值，换主题不再改代码。

| | v0.5 | v0.6.1 |
|---|---|---|
| 换主色 | 改 `Color.kt` 重新编译 | 设置里点一下，立刻生效 |
| 切 Tab | 蓝色 → 灰色（换色系） | **背景色完全一致，不跳** |
| 规划屏 | 永远是无彩深灰 | 跟其余三个面同一底色 |

五套预设：**靛蓝 / 墨绿 / 赭石 / 藕粉 / 岩灰**。

**为什么不做「自选任意颜色」**：好看在于配色是调出来的，不是算出来的。开放调色盘，派生色会有一半达不到对比度 —— 到时候界面上会出现读不清的字，而用户不知道为什么。这五套的主色都是手工压过亮度的。

**为什么最初规划屏是深色，后来又不是了**：v0.6 留了明度差，理由是睡前低刺激。用过之后发现那个理由站不住 —— 四个 Tab 里三个是浅的，只有规划屏整屏翻黑，切过去像进了另一个 App。**一个「统一」的界面里不该有一个例外，哪怕那个例外有道理。** v0.6.1 把这一档撤掉，四个 Tab 背景完全一致。

v0.7 又把深档请回来了，但换了个判断依据：**不再是「你在哪一屏」，而是「你自己要不要」**。顶栏一个 ☾，按一下四屏同时暗，再按一下同时亮。同一件事，按屏幕自动切换是打扰，按用户手动切换是尊重 —— 差别不在深色本身，在谁做决定。

### 二、背景图

从相册选一张，铺在**所有** Tab 下面。

三个实现上的取舍：

1. **一定要压遮罩**（默认 α 0.88，可在设置里调）。任何一张照片的明暗分布都是随机的，不压一层背景色，正文对比度就没法保证。
2. **每个 Tab 都铺**。既然是「统一」，就不能有一屏偷偷用纯色。
3. **图片存私有目录、库里只存文件名**。绝对路径里带包名和用户 id，换设备或恢复备份必然失效。

选图走系统 Photo Picker，**不需要任何存储权限**。

清晰度可调（v0.8）：设置里一根滑杆，遮罩 **0（纯图）**～ 0.96（最淡），默认 0.88；夜间自动再厚一档（+0.05）。同时把导入分辨率从 1600 提到 **2560** —— 背景是 `ContentScale.Crop` 铺满屏幕的，1600 长边的图铺 1080×2400 竖屏要放大 2 倍，只调遮罩救不回来。详见「v0.8：背景清晰度」。

能拖到 0 是 v0.10 的事。那种浓度下全屏遮罩已经不存在了，字改由「内容面板」（一块四边留缝的半透明圆角底）托住 —— 详见「v0.10：纯背景图」。

### 三、标签从「算法统计」改成「自己的」

v0.5 的标签是从历史备注里按频率算出来的前 8 个。v0.6 按你的要求改掉：

- 内置 8 个：午饭 / 早饭 / 晚饭 / 咖啡 / 地铁 / 打车 / 超市 / 房租
- 「+ 自己写」旁边多一个「**存为标签**」，写一次就能永久留下
- 长按任意标签 → 管理面板：删、加

**存哪里：SharedPreferences 一段 JSON，不建表。**
标签是配置，不是账目数据。建表就要写迁移，而迁移是本工程唯一可能丢数据的动作 —— 为了存几个字符串去动账本结构，代价和收益不成比例。配置坏了最多丢标签，账本永远完好。

**删标签不删账**：账目里存的始终是备注文本，标签只是往那个框里填字的快捷方式。这句话也写在了管理面板里。

### 四、日记

第四个面。**一天一篇**，`date` 直接做主键。

| 有什么 | 没有什么 |
|---|---|
| 多行正文，不限长度 | 分类 |
| 心情 5 档（可空，再点一次取消） | 标签 |
| 配图 1 张 | 搜索 |
| 停笔 800ms 自动保存 | 「保存」按钮 |

最后一条是关键：写日记时手一停就要点一次保存，那个动作本身就打断思路。这里改成自动存 —— 用户永远不用想「存了没」。

翻页前会先把手上这篇落盘再走，否则「写完马上翻走」会丢最后 800ms 的内容。

**这是本工程第一次真正新增第二张表**：`AppDatabase` 从 v2 升到 v3，手写 `MIGRATION_2_3`。前几版之所以能一直不动结构，是因为月历和标签都能靠查询解决；日记是全新的数据类型，绕不过去。

## v0.7：夜间模式

顶栏右上角，一个 ☾。按一下四屏一起暗，再按一下一起亮，状态存在本机。

### 为什么它该常驻在顶栏

因为它天天要用，而且用的时机很具体 —— **「现在这一刻光线不对」**。那一刻再去切设置、找到开关、切回来，光已经不对了。所以它宁可和「设置」并排放着，占掉顶栏一小块位置。

代价是顶栏本来就满：四个 Tab 加两个入口。实测一个符号宽度的挤压，比每次多跳两次值得。

### 一个符号，两种亮度

符号永远是月亮，**不会变成太阳**。

如果跟着状态换图标，用户每次都要先想一遍「这个太阳是表示现在是白天，还是表示点一下会变成白天」—— 这题没有标准答案，两种设计都有人用。所以干脆不换：灰月亮 = 关，主色月亮 + 一圈淡主色底 = 开。像手电筒按钮，一看就懂。

### 三处会被「底色反转」带偏的地方

加一个夜间模式，真正的工作量不在配色，在这三处：

| 位置 | 会怎么坏 | 处理 |
|---|---|---|
| **状态栏图标** | `enableEdgeToEdge()` 默认按**系统**深色设置决定图标黑白，和 App 内开关不同步 —— 系统浅色 + App 夜间时，那排深色图标整个消失在深底上 | 手动按开关设 `isAppearanceLightStatusBars` |
| **月历格子** | 如果字色写死「深色」，夜间档整屏看不见数字 | 字色一律取 `onBackground`，由主题在两端各配一次 |
| **设置里的色点** | 一直显示浅档的主色，而夜间实际用的是提亮过的那一档，选完发现颜色对不上 | 色点跟随当前模式显示 |

第一项最容易被漏掉，因为编译能过、界面能开、只有状态栏那一行是空的。

### 背景图在夜里怎么办

**照铺，只是在用户选的基础上再加厚 0.05。**

换个方向做（夜间干脆不铺图）更省事，但那就又给夜间开了个例外 —— 和 v0.6.1 刚收掉的那个毛病是同一个。用户调到最淡（0.96）时加厚会被截住，退化成日夜一样，不报错。

### 不跟随系统深色模式

系统的深色设置管整个手机，这个开关只管这四个 Tab。两个口径混在一起，就会出现「我明明关掉了它却还是黑的」，而用户找不到原因。所以：**明暗只有一个判断者，就是这个开关。**

## v0.8：背景清晰度

需求原话是「把背景的清晰度变成可调节的」。第一版方案只做了一件事——加一根控制遮罩浓度的滑杆——翻代码时发现漏了更重要的一半。

### 不清有两个原因，滑杆只能修一个

| 原因 | v0.7 的状况 | 后果 |
|---|---|---|
| **遮罩太厚** | 固定 0.88，图只剩 12% 透出来 | 图被压没了 |
| **分辨率不够** | 导入时长边压到 1600px | 图被放大 2 倍，边缘发软 |

背景图是 `ContentScale.Crop` 铺满整屏的。要铺满 1080×2400 的竖屏，一张 4:3 横图的**高**必须 ≥ 2400，也就是长边 ≥ 3200；1600 长边的图高只有 1200，等于放大 2 倍去看。**所以只调遮罩，拉到最清楚也还是糊。**

两个都改了：遮罩可调，导入分辨率 1600 → **2560**（图高 1920，放大约 1.25 倍，肉眼基本看不出插值）。内存从 7.3MB 涨到 18.7MB，一张全屏背景换这个清晰度，值。

### 滑杆的四个决定

1. **范围 0.75 ～ 0.96，默认 0.88。** 下限 0.75 是「图透出四分之一、显著但正文会发灰」的位置；再往下就该直接点「移除」了。默认值精确对齐 v0.7，装完不动的话看起来一模一样。
2. **一个滑杆，日夜联动。** 用户要表达的只有一句「图该清楚到什么程度」，夜里自动退一档就够了。做两个滑杆等于让同一件事理解两遍。
3. **存的是遮罩 alpha，不是「清晰度百分比」。** 真正生效的就是它，`prefs` 里看到 0.88 就知道是什么，不用反推。滑杆方向与遮罩反向（往右拖 = alpha 变小 = 图更清楚），这个换算只出现在 `ClaritySlider` 一处。
4. **不显示百分比，显示「偏淡 / 适中 / 清楚」。** 百分比会被读成「清晰度只有 38%」，而真实含义是「遮罩浓度 88%」——那种数字只会让人想凑个整。

### 旧图不会自动变清晰

分辨率是**导入那一刻**定下的。改 `MAX_DIMEN` 只影响以后新选的图，已经存下的 1600px 文件不会变。设置里写了一句实话：「以前选过的图是按较低分辨率存的，觉得糊就重新选一次。」

## v0.9：数据导出与迁移

需求原话是「在加一个数据导出，可以做数据迁移」。这句话里其实是**两个目的相反的功能**：

| | 给谁用 | 换手机时有用吗 |
|---|---|---|
| **导出**（csv） | 人 —— Excel 打开能核对 | 没用，读不回去 |
| **备份**（json + 图片） | App 自己 —— 能恢复 | 有用 |

只做前者，备份文件在换机那一刻就是废纸；只做后者，用户没法自己核对导出了什么。
所以一份 zip 里同时装两样：`data.json` 给 App 读回去，三个 `.csv` 给人看。

### 要导的东西比「三张表」多

| 内容 | 存在哪 | 不导会怎样 |
|---|---|---|
| 任务 / 账目 / 日记 | 数据库三张表 | —— |
| 日记配图、背景图 | `filesDir/journal`、`filesDir/theme` | 日记恢复后全部是空白图位 |
| 色板 / 夜间 / 清晰度 / 标签 / 背景图名 | SharedPreferences | 新手机上回到默认靛蓝，标签重来一遍 |

最后一行最容易漏：它不在数据库里，但它决定了「换机之后还是不是同一个 App」。

**只带被引用到的图片。** 目录里可能躺着换图时没删干净的旧文件，全目录打包等于把没人看的大图一起攒进备份。

### 为什么是 zip，不是一个大 json

图片转 base64 内嵌会让体积膨胀三分之一，更要紧的是**读的时候要整个进内存**：
一百张 2560 长边的配图，解码那一刻就是几十 MB 的字符串 —— 这正是这个工程一直在躲的那种崩法。
zip 是一个条目流式写、流式读的，同样的内容内存占用是个位数 MB。

### 恢复为什么只有「合并」，没有「覆盖」

覆盖是一个不可撤销的写操作，而它对应的场景（「我只想要备份里的那份」）可以靠
「先导出当前数据再恢复」达到 —— 代价是两步，收益是删不掉的东西。
一个自用 App 里不值得为了省一步，留一条能清空全部数据、又没有回收站的路径。

判重键是**业务字段的组合**，不是 id（id 是本机自增的，跨机器毫无意义）：

```
任务    planDate | content | orderIndex | createdAt
账目    date | amountCents | note | createdAt
日记    date 就是主键 → 同一天取 updatedAt 较大的那篇
```

任务的键里带 `content` 和 `orderIndex` 是故意的。只用 `planDate + createdAt` 的话，
一份 `createdAt` 全为 0 的老数据会把同一天的多件事判成同一件，**静默丢数据**。
**宁可重复也不要丢** —— 重复看得见，丢了看不见。

### 三道关卡，一道都不能少

1. **先解析出摘要**：任务 / 账目 / 日记 / 配图 四个数字，还写上导出时间和来源版本。
   用户在这一屏的判断是「这真是我要恢复的那份吗」——数字对不上（比如日记是 0 而自己写过半年）就会当场取消。
2. **格式与版本校验**：`format` 不是 `tonight-backup` 直接拒绝；`formatVersion` 比当前版本新，
   提示去升级 App，而不是硬着头皮读一半。
3. **三张表一个事务**：中途失败整批回滚，不会出现「任务导进去了、账目没有」这种半套状态。
   那种状态比彻底失败更难收拾 —— 用户不知道该再导一次还是不该。

### 两个顺序上的细节

**图片先落盘，数据库后写。** 反过来一旦中途失败，日记里就会留下指向不存在文件的 `imageName`，
界面上表现为一个永远空着的图位；现在这个顺序最多留几个没人引用的孤儿文件，用户看不见。

**导出先打包，再问存哪。** 系统文件选择器是异步的：先问再打包，选择器关闭后界面还要空转几秒，
那几秒里用户以为卡死了。

### 零权限

导出走 `ACTION_CREATE_DOCUMENT`，恢复走 `ACTION_OPEN_DOCUMENT`：
能读写哪个文件由用户在系统界面里当场指定。所以这个 App 至今 **`uses-permission` 一条都没有**，
也不需要 FileProvider。

### 自证：10 个单元测试

备份的写入与读取只用到 `java.util.zip` 和 `org.json`，**完全不依赖 Android** ——
于是它成了这个 App 里少数几件能在编译阶段就自证的事：

```
> ./gradlew :app:testDebugUnitTest

BackupRoundTripTest  10 tests, 0 failed
```

挡住的都是「编译能过、上手机才发现」的错：键名写错一个字母（每次恢复少一列）、
CSV 少了 BOM（Excel 全是乱码）、图片条目路径不对（日记配图恢复完全部空白）。
10 个用例里还有一个是故意写坏的 —— 断言「随便一个 zip / 一个更新版本的备份」会被**拒绝**，
并且给的是一句人话，不是 `ZipException` 的原文。

> 测试用的 `org.json` 只是为了替掉 JVM 上那份「调用即抛异常」的 android.jar 桩，
> 它不在 APK 里 —— **运行时依然零第三方依赖**。

## v0.10：纯背景图

需求原话是「背景始终有一个滤镜的那种，我要能实现到最后是完全是背景图那种形式」。

### 那个「始终有一层」是硬编码出来的

v0.8 把滑杆下限写成 **0.75**，理由是「再薄正文会明显发灰」。这个理由本身没错，
错在它把两件事绑成了一根杠杆：**遮罩既是「图淡不淡」的唯一旋钮，也是「字看不看得清」的唯一保障。**
一根杠杆管两个目标，就必然两头都不到位 —— 滑杆叫「清晰度」，却永远给不出 100%。

所以 v0.10 不是把 0.75 改成 0 就完了，而是先把这两件事拆开：

| 目标 | 由谁负责 |
|---|---|
| 图透出多少 | 全屏遮罩（滑杆，可以到 0） |
| 字能不能读 | 内容面板（一块半透明的圆角底） |

拆开之后，「拖到底 = 屏幕上只剩这张图」才成为一个可以成立的状态。

### 内容面板长什么样

不是「再加一层膜」，区别在于**它不铺满屏幕**：四边各留 10dp，图从边缘一直露到面板的圆角边上。
视觉上读作「图片是桌面，内容是一张纸」，而不是「整屏蒙了一层色」。

浓度是**跟着遮罩反向走**的：

```
遮罩 ≥ 0.75（默认档及更淡）→ 面板 α = 0     ← 那种浓度下正文本来就没问题
遮罩 = 0（纯图档）          → 面板 α = 0.52   ← 白天
                            → 面板 α = 0.66   ← 夜间（浅字在亮图上掉得比深字在暗图上快）
中间                        → 按比例过渡，所以是渐显
```

0.52 这个数是为了「哪怕照片是纯黑，面板下的底色亮度也在 120 以上」——
深色正文 `#1A1A1A` 压上去对比度仍有约 5:1，过线但不过分厚。

**默认档（0.88）下面板是 0**，所以装完不动的话，看起来和 v0.9 完全一样。
新东西只在用户主动把滑杆往左拖的时候才出现。

### 两条很少人想到的边

**其一：状态栏图标。** 面板让出的那圈缝，露出的是**一点都没压过**的图。
状态栏和导航栏的图标正好压在这圈缝上，而它们的黑白只由那一个月亮开关决定 ——
它不可能知道底下这张照片是亮是暗。夜里配一张亮图，白色图标会整个消失。
所以上下各压一条 64dp 的渐变，浓度和面板一致，视觉上几乎不构成「滤镜」，但足以让那排图标有依托。

**其二：夜间那档额外厚度会做出台阶。** 第一版写成 `if (night && dim > 0)`，
意思很清楚，但结果是滑杆在 0 和 0.005 之间，遮罩从 0 跳到 0.055 ——
拖到最左时画面**突然暗一截**。而人眼对「最后一格突变」极其敏感，那正是这一版要修的毛病。

改成缓入：额外厚度在离开纯图档的头 10% 滑程里从 0 长满到 0.05。
过了这 10%，行为和以前一模一样。

这个问题是脚本抓出来的，不是看代码看出来的 —— 见 `verify_dim_curve.py`：

```
白天：单步最大跳变 0.00500
夜间：单步最大跳变 0.04840   ← 改之前，红了
夜间：单步最大跳变 0.00660   ← 缓入之后
```

脚本直接**从源码里读常量**，而不是把数字抄一遍 —— 抄一遍就测不到「改了常量忘了改文档」。
另外它断言了三件事：默认值没被顺手改（否则老用户升级后外观会变）、
纯图档下面板不薄于设计值、最淡档下面板确实归零。

## v0.11：桌面小组件

一个 4×2 的组件：左半边今天要做的事，右半边今天花了多少。点任务前的圈可以直接勾掉。

### 先说清楚：它不能像 App 里那样实时

这是小组件最容易被误解的地方，也是这一版大部分设计的由来：

| 情况 | 组件的行为 |
|---|---|
| 在 App 里改了数据 | **立刻变**：数据一变就主动推一次（不是靠定时） |
| 关掉 App 什么都不做 | 系统最少 30 分钟调度一次，且**不保证按时** |
| 跨过零点 | 不会自己变成「第二天」，要等下一次刷新 |
| 在桌面上勾掉 | 写库 + 重绘，链路比「跳转」长 |

所以它的定位是**「瞥一眼」而不是「操作台」**。想让它替 App 记事，会一直觉得「怎么没反应」。

### 三个技术选择

**一、RemoteViews，不引入 Glance。**
项目的「零运行时第三方依赖」到 v0.11 仍然成立。Glance 是官方的 Compose for widgets，写法漂亮，但要新增依赖并和现有 Compose BOM 做版本协商。这个组件的全部内容是三行文字、一个数字、一条竖线 —— 没有一处非 Compose 不可。

**二、卡片底只有两张 drawable，不是十张。**
五套色板 × 明暗是十种组合，但五套的 `light.background` 分别是 `#FAFAF8` `#F9FBF8` `#FCFAF6`…，肉眼分不出来。做十份只是给以后留十个要同步改的地方。色板体现在**文字和金额**上（`accent` 每套都不同），那才是看得出的差异。

**三、不用 `setColorFilter` 染色。**
它是个反射调用，在 launcher 进程里执行，失败时不会抛到 App 里 —— 只会静默不生效，表现是「一块纯白卡片」，夜间档直接变成白底浅字。改用 `setImageViewResource` 换 drawable，是专用 API，没有这个风险。

### 三处容易做错的地方

**PendingIntent 的唯一性靠 data，不靠 requestCode。**
`requestCode` 是 `Int`，`taskId` 是 `Long`。用 requestCode 区分会截断，两条不同的任务共用一个 PendingIntent，表现是「点 A 勾了 B」，而且只在任务 id 足够大时才出现 —— 那种 bug 测不出来。所以用 `tonight://widget/task/<id>` 做 data。

**勾任务走仓储，不裸写 SQL。**
直接 `UPDATE tasks SET status=...` 会绕过 `completedAt` 和 `updatedAt` 的维护，导出的备份里就会出现「已勾选但没有完成时间」的记录。所以调的是 `TaskRepository.complete()` / `reopen()`。

**自定义 action 不进 intent-filter。**
PendingIntent 用显式 Intent，不需要 action 匹配就能送达。写进 filter 反倒是把「勾任务」这个动作暴露给任何能发广播的 App。所以清单里只声明 `APPWIDGET_UPDATE`。

### 「点了没反应」的两个来源

**`onNewIntent` 必须重写。** App 已经开着时点组件，`singleTop + CLEAR_TOP` 会复用当前实例、只送来一个新的 Intent。没人接就等于没发生。

**落点判断会让路。** `MainViewModel` 的 init 里有个异步的「今天有没有没做完的事」判断，它会在几十毫秒后才写 tab。如果这时小组件已经点名要「记账」，那个判断会把它覆盖回去 —— 表现是一瞬间跳到别的屏，几乎无法复现。所以加了 `explicit` 标记：**明确指定 > 自动判断**。这条规则对用户点 Tab 同样成立。

### 行数跟着组件高度变

`minSdk 26` 上做不到「随尺寸换布局」（那是 API 31 的响应式），但可以**改变行数**：

```
110dp（标准 4×2）→ 3 行任务 · 1 笔账
135dp 以上      → 4 行任务 · 2 笔账
165dp 以上      → 5 行任务 · 2 笔账
```

用户把组件拉高，就多看见几件事，而不是把三行字拉成三行更大的字。

### 一条没做到的：已完成的划线

设计稿里已完成的任务是带删除线的。RemoteViews **没有官方的划线 API**，唯一的路是 `setInt(id, "setPaintFlags", ...)` 这个反射调用 —— 和上面 `setColorFilter` 是同一类风险，而且 `setPaintFlags` 会覆盖原有的 `ANTI_ALIAS_FLAG`，文字发毛。

所以放弃了划线，改用**实心圆点 + 文字变淡**。信息量没少，只是弱了一点。

## v0.12：四种卡片

同一个组件拆成四种规格，长按桌面 →「小组件」里能看到四个「今晚」：

| 卡片 | 格数 | 最小尺寸 | 内容 |
|---|---|---|---|
| **今晚 · 今天** | 4×2 | 250 × 110dp | 左 3 行任务 / 分隔线 / 右金额 + 1 笔 |
| **今晚 · 宽版** | 5×2 | 320 × 110dp | 同上，每行多显示约两个字 |
| **今晚 · 待办** | 3×2 | 180 × 110dp | 只有任务，3 行，一行约 10 字 |
| **今晚 · 记账** | 2×2 | 110 × 110dp | 只有金额 + 2 笔 |

### 四张卡必须是四个类，不是一份布局配四份配置

一个 `receiver` 只能挂**一个** `meta-data`，而网格尺寸就写在那一份 `AppWidgetProviderInfo` 里。想让选择列表里出现四种规格，就只能注册四个组件。

它们共用同一套渲染（`BaseWidgetProvider` + `WidgetRenderer`），子类只声明三件事：布局 id、任务行数、账目笔数。**行数返回 0 就等于「这张卡没有这块区域」** —— 渲染层据此决定要不要去碰 `task_label` / `money_sum` 这些 id。用 0 而不是再加一个布尔开关，是因为「有没有这块区域」和「这块区域放几行」本来就是同一件事，拆成两个字段迟早会出现「说有区域但行数是 0」的矛盾状态。

### 5×2 和 4×2 共用一份布局

两张卡高度都是 2 格 = 110dp，行数规则完全一样。宽度差异由 `match_parent` 自适应 —— 多写一份布局只会多一个要同步维护的地方，而差异是零。

### 2×2 的金额用 autoSize

2 格宽只有 110dp，扣掉内边距剩 **82dp**。「¥128.50」在 24sp 下放得下，「¥1,234.56」放不下。固定字号只会在四位数以上那几天突然截断，而截断的样子（「¥1,23…」）看起来像**账算错了**，不像「字太大了」。

`autoSizeTextType` 是 API 26 引入的，正好等于 `minSdk`，所以直接用 `android:` 命名空间的属性就够，不需要 AppCompat。

### 刷新只写一处，但必须刷全部

`TonightApp` 里一个 `InvalidationTracker` 监听三张表，任何写入都触发 `WidgetRefresher.refreshAll()`，它遍历 **四个** `ComponentName` 各自的 id 列表。

为什么不能「哪个组件收到广播就只刷它自己」：同一条任务可能同时出现在 3×2、4×2、5×2 三张卡上。在 3×2 上勾掉它，另外两张不跟着变，用户看到的就是「我明明勾了，另一块还是没勾」—— 这种不一致比完全不刷新更让人怀疑数据到底存没存上。

`WidgetRefresher.PROVIDERS` 这个列表漏一个的后果是「那张卡永远不会自己更新」，而且只表现为偶发不对。`verify_widget.py` 会把它和 AndroidManifest 里的 `receiver` 做一一对应核对。

### 有一件东西不能动：老 provider 的类名

`TonightWidgetProvider` 这个名字不能改、不能删。已经添加到桌面的 4×2 卡片把 `ComponentName` 写死在系统里，改名或删类会让它们变成「无法加载」，用户得手动移除再重新添加。

## v0.13：日记日历

日记屏从 v0.6 起就是「一天一页 + 两个箭头」。写到第三个月就露馅了：**想找上周三那篇，得按七次「←」，而且按到之后还得自己确认是不是那一天。**

日历要回答的只有一个问题 —— **哪几天写过**。有了这个，往回找就从「逐天试探」变成「看一眼、点一下」。

### 为什么是整屏切换，不是弹层也不是第五个 Tab

弹层看着更轻，但月历本身要占 5~6 行 × 44dp，加头部已经是半屏以上，做成弹层就是「一个几乎全屏的弹层」，只是多了一层滑动动画和一层遮罩。

第五个 Tab 更不行：日记的默认入口必须是**今天**。日历是「往回找」时才走的路，不是并列的一种日常用法 —— 放进 Tab 会把「打开就写」变成「先选个什么」。

所以它藏在日期行最右边一个「日历」文字按钮里，点开整屏换成月历，点「完成」回来。

### 为什么是小圆点，不是深浅

记账月历用底色深浅表示「这天花了多少」，那是账目天生有的东西 —— **金额可以比大小**。

日记没有。写三行和写三屏都是「写了」，而且**三行那天可能才是唯一值得记的一天**（加班到十一点，只写了一句「今天不想说话」）。用深浅编码字数，会让这种日子在月历上看起来像废稿。

所以只有「有 / 没有」两态：天号下面一个 4dp 圆点。

顺带还有第二层编码：写过的天号用正文色，没写过的用次要色。**和圆点说的是同一件事，但这是有意的** —— 纯图档（遮罩拖到 0）时圆点可能被照片吃掉，字色的差别不会。两层里掉一层还剩一层。

### 两条 SQL 看同一件事，条件必须同源

「哪天写过」和「往回翻的时间线」是同一件事的两个入口，因此是两条不同的 SQL：

```sql
SELECT *    FROM journal WHERE content != '' OR imageName IS NOT NULL ORDER BY date DESC
SELECT date FROM journal WHERE content != '' OR imageName IS NOT NULL ORDER BY date DESC
```

如果这两处的过滤条件漂了一点点，就会出现**日历上有点、点进去是空白页**。它不崩、不报错，看起来像「日记丢了」—— 而查起来要从 UI 翻回 DAO。

所以条件抽成了一个常量 `WRITTEN`，两条 `@Query` 都拼它。这比「写两遍然后记得同步」可靠：**不一致在语法层就不可能出现**，不依赖任何人记得。`verify_journal_calendar.py` 再补一道断言 —— 任何 `@Query` 里出现 `content !=` 字面量就算失败。

### 顺手修掉的一个错位写库

加日历的时候发现一个从 v0.6 就存在的隐患。

切日期是**先落盘、再改 `_viewDate`**，而加载新一天的内容是异步的。这中间有一个窗口：`_viewDate` 已经翻到新日期，`_content` 还是上一天的字。

逐天点箭头时，这个窗口只有几毫秒，手速撞不上。但日历一下能跳二十天，**连点两格就正好落在里面** —— 结果是 `persist()` 拿 `_viewDate.value` 当日期，把 A 天的正文写进 B 天。不崩、不报错，只是两篇日记互相串了内容。

修法不是加锁，而是**让内容自己记住它属于哪一天**：

```kotlin
/** 手上这段字属于哪一天。只在真正加载完某一天的内容时才变，不跟着 _viewDate 走 */
private var contentDate: LocalDate = today
```

所有 `persist()` 的第一个参数一律用 `contentDate`。这样即使日期的值已经走在前面，落盘日期也永远是「这段字本来属于的那天」。脚本断言三处调用点全部如此，且 `goTo()` 里 `persist` 在 `_viewDate = target` **之前**。

另外，翻页箭头和日历格子原来是两条路。现在都走 `goTo(date)` 一个函数 —— 落盘逻辑只有一份，新加入口时不可能忘掉那 800ms。

### 未来日期点不动

日历能往前翻（翻到去年的空月份也没关系），但未来那几格变淡且点不进去。

理由很实际：**能点进去，用户就会写下一篇永远不会再被翻到的日记**。它只会在「往回找」时被跳过，因为那天根本还没到。

- **今天 / 规划 / 记账 / 日记** 四个面底色永远一致

## 记账的几个决定

**1. 汇总卡锚定「真正的今天」，不跟着明细往回翻。**
明细可以一直往回走去看历史，但顶部那张卡永远算的是**今天 / 本周 / 本月**。
如果卡片跟着明细走，翻到上周三时它会变成「上周三 / 那一周 / 那个月」—— 三个数字全换了意思，而你以为自己看的是「我今天花了多少」。这是最容易被忽略、但一定会踩的一个坑。

**2. 不能翻到未来。**
未来的账不存在，能翻过去只会让人怀疑数据。所以日视图的「→」到今天就到底，月视图的「→」到当月就到底。

**3. 日期导航就是输入日期，备注优先给标签。**
「`← 今天 · 10/21 →`」那一行的日期，同时也是你这一笔记在哪天 ——
所以**补记不需要再选一次日期**，往回翻一天直接写就行。
备注则优先点标签（内置八个，自己存的会一直留着），
偶尔要写新的才点「+ 自己写」—— 需要打字是例外，不是常态。

**4. 金额一律用整数存（单位「分」）。**
`Double` 表示不了 0.1，二进制浮点累加到月总额就会和实际对不上。所以数据库、领域模型、聚合 SQL 全程是 `Long` 的「分」，**只有输入和显示两个端点才出现「元」**。这条约束在代码里是一路贯穿的，不是只写在数据库那一层。

**5. 输入看不懂就说看不懂，不猜。**
`32`、`32.5`、`32.50` 都收；`32.567`、`abc`、负数一律拒绝并提示。
刻意不做「悄悄四舍五入成 32.57」这种事 —— 账本上最不该有的就是系统替你改过的数字。

**6. 删除是真删，不是打标记 —— 但入口藏进了编辑态。**
账记错了就是记错了。留一堆看不见的墓碑，只会让「本月合计」和明细对不上时更难查。
既然是真删、不可撤销，那它就不该是一个常驻在每行右边、正好落在手指上的「×」。
现在要删一笔：先点开那一行，再点「删」。多一次点击，换掉「手滑就没了一笔账」。

**7. 周和月的边界是人在过的日子。**
本周 = **周一 00:00 起**（不是周日），本月 = 1 号到月末。理由是发工资、还信用卡、看账单的周期都是周一，
「本周花了多少」必须和你脑子里的那个「本周」是同一个区间 —— 否则数字对上了，直觉对不上。
月历的第一列同样放**周一**，不然「本周」和月历上的行对不上。

**8. 月历格子里的金额只到「元」，上千用 k。**
一格只有 44dp 宽，`¥128.50` 塞不进去。丢掉的分只影响这一个格子的观感 ——
合计和明细仍然精确到分。月历是拿来看分布的，不是拿来对账的；对账有明细和汇总。

### 几个关键设计

**1. 三张表，各管各的**
`tasks` / `expenses` / `journal` 是三张独立的表，不 join、不互相引用。UI 只认 `Task` / `Expense` / `Journal` 三个领域模型，Room 的 Entity 封在 Repository 内部。
换存储引擎、加云同步，UI 一行不用改。

唯一共享的东西是「日期」这个字符串的格式（`yyyy-MM-dd`）—— 这让「某一天都发生了什么」将来可以靠三次独立查询拼出来，而不必现在就把三张表绑死。

**2. 全链路 Flow**
Room 数据一变，界面自动刷新。记完一笔，三个合计和当前月历由各自独立的聚合查询重算 —— 没有手动 `refresh()`，也没有缓存的合计。

**3. 月历的聚合交给 SQLite，不捞回内存再分组**
月历只要 31 个数字，没必要为它把整月明细查上来。账本是「只增不减」的数据，一年就是几千行 —— 这个区别会逐年变明显。

**4. 调序是「按位重写」，不是「交换两条」**
上移 / 下移时把当天的清单整段重写成 `1..n`，而不是只交换相邻两条的 `orderIndex`。
历史数据里 `orderIndex` 有可能重复（两次 `add` 撞上同一个 `max` 时就会），交换只会把重复值原样留下；逐位重写才能保证序列一直是干净的。

**5. 行内动作不用图标库**
`↑ ↓ × ✓ ← →` 几个字符就够用，省下一个依赖和一堆矢量资源。同时因为它是 `Text` 而不是 `IconButton`，尺寸小、不抢注意力 —— 一行里的次要动作不该长得比内容还显眼。

**6. 依赖只有一条链，不引额外框架**
没引入 Hilt、没引入 Navigation、没引入图表库。屏幕只有三个、依赖链只有一条，引库的收益接近零、成本是一层抽象。这个判断写在代码注释里。

| v0.10 | 3 | **无迁移**。纯图档改的是 `bg_dim` 的**取值范围**（0.75~0.96 → 0~0.96），一个字段都没碰 |
| v0.11 | 3 | **无迁移**。小组件只给 `ExpenseDao` 加了两个 suspend 一次性查询（`getByDate` / `getSum`），表定义没动 |
| v0.12 | 3 | **无迁移**。四张卡只改渲染与注册，一行 SQL 都没写 |
| v0.13 | 3 | **无迁移**。日历只给 `JournalDao` 加了一条 `SELECT date`（复用时间线那套过滤条件），表定义没动 |

这五次「无迁移」不是巧合，是设计时第一个要想的问题：**这件事能不能不动结构就做完？**
能不动，安装风险就是零 —— 不用赌迁移写对没写对。

关于 v0.3 那次真迁移，有一点值得说清楚：

- 如果迁移 SQL 与 Room 期望的结构不一致，Room 会在**打开数据库时直接抛异常、App 闪退** ——
  问题当场暴露，而**数据库文件是完好的，数据还在**。
- 真正会导致**静默清库**的只有 `fallbackToDestructiveMigration()`（结构对不上就把库删了重建）。
  **本工程从头到尾没有用它，也不打算用。** 宁可崩给你看，也不能悄悄清掉你的账。

`app/schemas/` 目录是 Room 导出的**结构基准**（由 KSP 生成，已提交进仓库）。
写迁移 SQL 时必须逐字对照它 —— 这是在**没有模拟器的机器上**唯一能自证「迁移结果与 Entity 期望一致」的手段。
反过来它也有一项用处：**没生成新的 schema 文件，就等于机器确认了「这一版没动结构」。**

## 已知边界（v0.13）

| 限制 | 说明 |
|---|---|
| **小组件不会实时刷新** | 在 App 里改数据会立刻同步；但关掉 App 后只能靠系统 30 分钟一次的调度，且不保证按时 |
| **四种规格是四个独立组件** | 4×2 / 5×2 / 3×2 / 2×2 各自的尺寸是写死的，彼此不能替代。「一张卡随尺寸换布局」要 API 31 |
| **5×2 不比 4×2 多看几条** | 两张卡高度都是 2 格，行数一样。宽度只让每行多放两个字 |
| **2×2 卡一行只放得下四个字** | 2 格宽 = 110dp，扣内边距剩 82dp。长备注会被截断，所以只给 2 笔 |
| 小组件只显示「今天」 | 看不了明天要做什么。想规划就去 App |
| 小组件里已完成的任务没有划线 | RemoteViews 没有官方划线 API，靠反射调 `setPaintFlags` 会覆盖抗锯齿标志、有崩溃风险。改用实心点 + 变淡 |
| 小组件里只能勾、不能改 | 改文字、删任务、记新账都要进 App |
| **备份不会自动做** | 没有定时任务、没有云同步。设置页只有一句「上次备份：…」 —— 提醒但不代劳 |
| **备份是明文 zip** | 不加密。里面有日记正文和照片，发给别人之前想一下 |
| 恢复只有「合并」 | 没有「清空后覆盖」。想整体回退，先导出当前数据再恢复 |
| 判重靠内容组合，不是时间戳 | 在另一台手机上改过内容的同一条任务，会被当成「新的一条」再插一次 —— 宁可重复也不丢 |
| 换机迁移要求同一个签名 | 备份本身是普通文件、与签名无关；但要让 App 装得上并读到自己的私有目录，得是同一个包名 + 同一个签名 |
| 只带被引用到的图片 | 目录里没人用的旧图不进包，所以备份大小 ≈ 实际用到的图 |
| 备份不校验业务一致性 | 例如 `orderIndex` 会重排成 1..n，但不会判断「这个日期是否合理」 |
| 旧背景图不会自动变清晰 | 分辨率是**导入那一刻**定下的。v0.7 及以前存的图仍是 1600px，觉得糊就重新选一张 |
| 纯图档下字会压在照片本身上 | 内容有面板托底，但**顶栏那圈缝和内容间隙是裸图**。挑一张明暗均匀的图，或者把滑杆留在中间档 |
| 面板是渐显的，临界处在 0.75 | 过了这个浓度面板整个消失。想让图更透又要有面板，就把滑杆停在 0.4 左右 |
| 面板厚度不给调 | 白天 0.52 / 夜间 0.66 是写死的。再加一根滑杆，等于让人同时调两个互相抵消的东西 |
| 背景清晰度只有一根滑杆 | 日夜不分开调：夜间自动在白天的基础上加厚 0.05（纯图档除外，且是 10% 滑程内缓入的） |
| 日记不能一天多篇 | 一天一段，想写长就写长。刻意不提供「新开一条」的选择 |
| 日记有日历，但没有列表页 | 日历回答「哪几天写过」，不回答「上个月都写了什么」。想连续翻着读还没有入口 |
| 日历不显示「写了多少」 | 只有一个小圆点表示写过。写三行和写三屏长得一样 —— 日记没有可比的量，用深浅会让人把短的那天当废稿 |
| 日历上心情不可见 | 哪天记了什么心情要进去才知道。把心情编码成颜色就得配图例，而图例本身要学 |
| 日记配图只有 1 张 | 多图会带来重排、删除、顺序三个新问题，先不做 |
| 记完一笔键盘会收起 | 想连着记几笔，每笔都要再点一次金额框 |
| 主题只有五套预设 | 不给自选颜色：派生色容易达不到对比度，而用户不会知道为什么字看不清 |
| 夜间模式不分时自动切 | 只能手按。想做「天黑自动切」得拿定位或系统日出日落，那是一个新权限 |
| 没有「跟随系统」选项 | 系统的深色管整机，这个开关只管这四个 Tab，两个口径混着会出现「我关了它还是黑的」 |
| 账目不能改归属日期 | 金额和备注可改，但不能把一笔账从今天挪到昨天 |
| 没有分类统计 | 月历看得出「哪天多」，看不出「花在什么上」 |
| 月历金额只到「元」 | 格子太窄，分被省略；合计和明细仍精确到分 |
| 没有提醒 | 需要通知权限 + 国产 ROM 后台保活 |
| 不能跨天挪任务 | 今天没做的不能一键挪到明天 —— 刻意不做，那会让「哪天做什么」变得可以随意篡改 |
| 跨天不自动刷新 | App 长期驻留后台跨过零点时，需重启一次。日历里「今天」那圈描边也会跟着错一格 —— 同一个原因 |

### 关于数据安全

数据全在本机，**卸载 App 会全部丢失** —— 任务、账目、日记、图片、主题设置，一个不剩。

v0.9 起有了后悔药：**设置 → 数据 → 备份到文件**，打成一个 zip 存到你选的位置
（可以是下载目录，也可以是网盘 App 的目录）。换手机时在新机上「从备份恢复」即可。

但备份**不会自己发生**。它失效的方式从来不是「不好用」，是「忘了」——
第一次备份常常发生在某一次后悔之后。设置页那行「上次备份：…」就是为这个留的。

1. **备份的自动化** —— 现在要人记得点。可以先做「超过 14 天没备份就在设置页显红」，再考虑自动导出到固定目录
