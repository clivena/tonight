# 今晚

> 今晚排好，明天照着做。

一个每日便签：**在你想规划的时候把要做的事写下来，第二天打开就是一份可以随手勾掉的清单。**

v0.3 起多了一个**独立的「记账」面**：记一笔花了多少，抬头就看到今日 / 本周 / 本月的合计。

- 平台：Android（`minSdk 26` / `targetSdk 35`）
- 技术：Kotlin + Jetpack Compose + Room
- 数据：纯本地存储，**无账号、无联网、无数据收集**
- 状态：v0.3，已编译验证（见「验证记录」）

---

## 为什么做这个

大多数待办 App 的逻辑是「帮你记住」。但真正消耗人的不是「记不住」，而是「**不知道该先做哪个**」。

于是它们给你列表、优先级、进度条 —— 让你在动手之前先做一轮排序决策。

这里想做的事正相反：**把「决定做什么、按什么顺序」提前到你精力还够的时候做完，第二天早上不用再想。**

## 从 v0.1 到 v0.2：三条硬规则的复盘

v0.1 为了把判断力消耗压到最低，定了三条硬规则：早上**只显示一件事**、一天**最多 5 件**、规划完**就结束**。

自己用了一周之后，三条全部出了问题 —— 不是理念错，是**手段太硬**：

| v0.1 的规则 | 真实使用中发生的事 |
|---|---|
| 早上只给一件事 | 排第一的那件暂时做不了（要等人回消息、环境没准备好），整天就卡死在那里，没有任何跳过的入口 |
| 一天最多 5 件 | 上限校验写成了「全部条数」而不是「未完成条数」—— 删掉一条想换一条，就再也加不回来了 |
| 规划完就结束 | 点完「就这样」停在一句「晚安」上，当天想再补一件事也进不去，只能杀掉 App |
| 计划写完不能改 | 错字、顺序不对、不想做了 —— 全都没办法 |

**这些不是理念错了，是把手段当成了目的。**

「不给选择」是手段，目的是「不消耗判断力」。而当手段本身开始消耗判断力 —— 还得记着别踩上限、还得祈祷第一件能做、还得担心写错一个字就废了 —— 它就从帮手变成了负担。

于是 v0.2 把三处硬规则拆掉，换成：

| 原来 | 现在 | 有意保留的是什么 |
|---|---|---|
| 只给一件 | 给完整清单，**任意顺序勾选** | 顺序仍是你自己排的，界面不做二次排序 |
| 最多 5 件 | **没有上限** | —— |
| 规划完就结束 | 顶部「今天 / 规划」**两个 Tab 随时互达** | 两个面气质不同：白天浅色，夜里深色 |
| 计划不能改 | 可改文字、可调顺序、可删除、可取消勾选 | —— |

一句话概括：**v0.1 帮你把决定做完，v0.2 允许你改主意。**

## v0.3：为什么记账是「另一个 Tab」

这个 App 从立项起就写了一条硬规则：**不做统计、不做分类标签**。因为这些东西都在增加判断力消耗。

而记账天生就是统计。所以 v0.3 没有把记账揉进任务流里，而是**把它做成第三个 Tab，和任务模块零耦合**：

- 任务屏不因为记账变复杂（还是那两栏，一个字没改）
- 记账屏也不受「减少判断」那条约束的管辖（记账本来就该允许你补记、允许你改）

**两个模块各自保持纯粹，拼在同一个 App 里但互不干涉。** 表也是两张，谁也不因为对方而多一个字段。

> 顺带一个判断：这次记账**只记支出**，不记收入。你说的需求是「每日总花了多少每周每月」——
> 把支出记准，就已经回答了这个问题；加上收入会把界面变成一张收支表，那就不是这个 App 该管的事了。

## 快速开始

### 方式 A：Android Studio（推荐）

1. Android Studio → **Open** → 选中本仓库根目录
2. 等待右下角 Gradle Sync 完成（首次会下载依赖）
3. 连接手机（开启「开发者选项 → USB 调试」），点绿色三角 Run

> 若提示缺少 SDK 组件，点提示里的安装即可。本项目在
> **Android SDK Platform 35** + **Build-Tools 34.0.0** 上编译通过。

### 方式 B：命令行（从仓库根目录执行）

```bash
# JDK 需 17+；Android Studio 自带的 JBR 即可
export JAVA_HOME="$LOCALAPPDATA/Programs/Android Studio/jbr"   # 路径按本机实际情况调整
export ANDROID_HOME="$LOCALAPPDATA/Android/Sdk"

./gradlew :app:assembleDebug
```

产物与安装：

```bash
# 产物
app/build/outputs/apk/debug/app-debug.apk

# 装到手机（USB 调试已开启）
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

> 也可以直接把 `app-debug.apk` 传到手机上点击安装（需允许「安装未知应用」）。

## 日常怎么用

| 时间 | 你做什么 | App 做什么 |
|---|---|---|
| 睡前 / 任何想规划的时候 | 切到「规划」，写下要做的事 | 深色界面，安静地收下 |
| 第二天 | 打开，默认落在「今天」 | 一份清单，随手勾 |
| 做着做着 | 想到新的事、想改一条 | 切到「规划」，改文字 / 挪顺序 / 删掉都行 |
| 花完钱 | 切到「记账」，输金额、写备注 | 抬头三个数字立刻更新 |
| 全勾完 | — | 清单底部一句「今天就这样。」 |

### 三个 Tab，两种气质

- **今天**是浅色：白天，要一眼看清
- **规划**是深色：睡前低刺激
- **记账**是浅色：和「今天」同族 —— 记账发生在花钱的当下，是白天的事

这两套主题是**写死的，不跟随系统深色模式**。因为深浅色在这里是功能，不是偏好 —— 若跟随系统，一个开着浅色模式的用户晚上会看到刺眼白屏，产品意图直接破功。

切换 Tab 时整屏会换色。这个跳变是有意的：三栏里只有「规划」是夜里那一面。

### 两个小决定

**勾完不倒着往下沉。** 清单的位置就是你排的位置，勾选不会让列表跳动。列表自己会跳的界面，人是记不住自己排的顺序的。

**复选框是双向的。** 勾上是完成，再点一下退回待做。勾错了没得救的清单，用两次就不敢用了。

## 记账的几个决定

**1. 汇总卡锚定「真正的今天」，不跟着明细往回翻。**
明细可以一直往回走去看历史，但顶部那张卡永远算的是**今天 / 本周 / 本月**。
如果卡片跟着明细走，翻到上周三时它会变成「上周三 / 那一周 / 那个月」—— 三个数字全换了意思，而你以为自己看的是「我今天花了多少」。这是最容易被忽略、但一定会踩的一个坑。

**2. 不能翻到未来。**
未来的账不存在，能翻过去只会让人怀疑数据。所以「→」到今天就到底。

**3. 记在什么时候，就记在什么时候。**
输入框下面那行字会明确告诉你「记在 今天」或「记在 昨天」，输入框跟着明细日期走 ——
所以**补记不需要再选一次日期**，往回翻一天直接写就行。

**4. 金额一律用整数存（单位「分」）。**
`Double` 表示不了 0.1，二进制浮点累加到月总额就会和实际对不上。所以数据库、领域模型、聚合 SQL 全程是 `Long` 的「分」，**只有输入和显示两个端点才出现「元」**。这条约束在代码里是一路贯穿的，不是只写在数据库那一层。

**5. 输入看不懂就说看不懂，不猜。**
`32`、`32.5`、`32.50` 都收；`32.567`、`abc`、负数一律拒绝并提示。
刻意不做「悄悄四舍五入成 32.57」这种事 —— 账本上最不该有的就是系统替你改过的数字。

**6. 删除是真删，不是打标记。**
账记错了就是记错了。留一堆看不见的墓碑，只会让「本月合计」和明细对不上时更难查。

**7. 存的是「分」，但周和月的边界是人在过的日子。**
本周 = **周一 00:00 起**（不是周日），本月 = 1 号到月末。理由是发工资、还信用卡、看账单的周期都是周一，
「本周花了多少」必须和你脑子里的那个「本周」是同一个区间 —— 否则数字对上了，直觉对不上。

### 几个关键设计

**1. 两张表，各管各的**
`tasks` 和 `expenses` 是两张独立的表，不 join、不互相引用。UI 只认 `Task` / `Expense` 两个领域模型，Room 的 Entity 封在 Repository 内部。
换存储引擎、加云同步，UI 一行不用改。

**2. 全链路 Flow**
Room 数据一变，界面自动刷新。记完一笔，三个合计由三条独立的聚合查询各自重算 —— 没有手动 `refresh()`，也没有缓存的合计。

**3. 调序是「按位重写」，不是「交换两条」**
上移/下移时把当天的清单整段重写成 `1..n`，而不是只交换相邻两条的 `orderIndex`。
历史数据里 `orderIndex` 有可能重复（两次 `add` 撞上同一个 `max` 时就会），交换只会把重复值原样留下；逐位重写才能保证序列一直是干净的。

**4. 行内动作不用图标库**
`↑ ↓ × ✓` 四个字符就够用，省下一个依赖和一堆矢量资源。同时因为它是 `Text` 而不是 `IconButton`，尺寸小、不抢注意力 —— 一行里的次要动作不该长得比内容还显眼。

**5. 依赖只有一条链，不引额外框架**
没引入 Hilt、没引入 Navigation。屏幕只有三个、依赖链只有一条，引库的收益接近零、成本是一层抽象。这个判断写在代码注释里。

## 关于数据库升级（v0.2 升级到 v0.3 必读）

v0.3 是本项目**第一次改动数据库结构**：

| 版本 | `AppDatabase.version` | 迁移 |
|---|---|---|
| v0.1 | 1 | —（首发） |
| v0.2 | 1 | **无迁移**。因为刻意没动表结构，覆盖安装即可，数据全部保留 |
| v0.3 | 2 | **有迁移** `MIGRATION_1_2`：只新增 `expenses` 表，`tasks` 表一个字段都没碰 |

关于这次升级，有一点值得说清楚：

- 如果迁移 SQL 与 Room 期望的结构不一致，Room 会在**打开数据库时直接抛异常、App 闪退** ——
  问题当场暴露，而**数据库文件是完好的，数据还在**。
- 真正会导致**静默清库**的只有 `fallbackToDestructiveMigration()`（结构对不上就把库删了重建）。
  **本工程从头到尾没有用它，也不打算用。** 宁可崩给你看，也不能悄悄清掉你的账。

所以这次迁移是「只加一张新表」这种最简单的类型，风险低，且失败模式是可见的崩溃而不是无声的丢失。

`app/schemas/` 目录是 Room 导出的**结构基准**（由 KSP 生成，已提交进仓库）。
写迁移 SQL 时必须逐字对照它 —— 这是在**没有模拟器的机器上**唯一能自证「迁移结果与 Entity 期望一致」的手段。
这个目录要一直保留：将来 v3、v4 的迁移都要拿它当基准。

## 已知边界（v0.3）

| 限制 | 说明 |
|---|---|
| **没有数据导出** | **这是目前最明显的缺口**，见下方 |
| 账目不能改归属日期 | 金额和备注可改，但不能把一笔账从今天挪到昨天 —— 改期是把账搬到另一天，属于另一个动作 |
| 没有分类统计 | 只有三个合计，没有「餐饮 / 交通 各占多少」。备注里写了什么，得自己翻 |
| 没有提醒 | 需要通知权限 + 国产 ROM 后台保活 |
| 不能跨天挪任务 | 今天没做的不能一键挪到明天，只能自己重写一条 —— 刻意不做，那会让「哪天做什么」变得可以随意篡改 |
| 没有历史回顾 | 数据都在，只是没有界面 |
| 跨天不自动刷新 | App 长期驻留后台跨过零点时，需重启一次 |

### 关于数据安全

数据全在本机，**卸载 App 会全部丢失**。
在加上「导出」功能之前，重要内容请自己另外记一份。
这是下一步的第一优先项 —— 它是唯一的后悔药。**而且现在数据从一类变成了两类，丢的代价翻倍。**

## 下一步

按价值排序：

1. **数据导出**（最该先做）—— 唯一的后悔药，而且现在要同时覆盖任务和账目
